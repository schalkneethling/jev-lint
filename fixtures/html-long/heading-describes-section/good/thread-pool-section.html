Tuning the service

Choosing a thread pool size

A few years ago I sat in the back row of a conference talk whose title I have forgotten, given by someone whose name I never wrote down, and the only thing I remember from it is a slide with a single sentence on it: measure the thing you are about to guess at. I have quoted that slide in more design reviews than I can count, usually to people who were about to spend an afternoon arguing about a number that a ten minute experiment would have settled. It is the least original advice in this entire handbook and it is still the advice that gets ignored most often, so here it is again at the top of a page where it applies.

For work that is purely on the processor, one worker per core is the starting point and anything above it trades throughput for context switches. For work that waits on a database or another service, the useful number is roughly the number of cores multiplied by one plus the ratio of waiting time to working time, which for our request handlers comes out somewhere between twenty and forty on an eight core box.

Whatever number you pick, bound the queue in front of the pool. An unbounded queue turns a slow dependency into unbounded memory growth and then into a process the kernel kills, and the graph that results looks like a memory leak rather than like the downstream timeout it actually is. A bounded queue that rejects work gives you a fast error and a metric you can alert on.
